## 2. Phân tích hiện trạng

### 2.1. Luồng xác thực hiện tại (và chỗ hở)

```
LOGIN  POST /api/auth/login {username,password}
  │  AuthController.login():
  │    ① kiểm tra khóa tạm bằng ConcurrentHashMap tĩnh (mất khi restart)
  │    ② AuthenticationManager.authenticate()      ← DisabledException nếu active=false
  │    ③ tokenProvider.generateToken()             ← ⚠ cấp JWT ĐẦY ĐỦ QUYỀN NGAY (dòng ~84)
  │    ④ nếu role ∈ {ADMIN, LECTURER, DEPARTMENT_ADMIN}: gửi OTP qua email
  │    ⑤ trả {token, ..., otpRequired:true}         ← ⚠ token đã dùng được
  ▼
FRONTEND (LoginPage): lưu token vào localStorage.temp_token, hiện ô OTP
  ▼
OTP    POST /api/auth/otp/verify {username, code}   → chỉ trả {verified:true|false}
  ⚠ Không cấp gì, không giới hạn số lần thử (10^6 mã, hạn 5 phút → dò được)
  ⚠ Kẻ biết mật khẩu chỉ cần dùng temp_token, KHÔNG cần OTP  →  smoke test 1a: HTTP 200

MỖI REQUEST SAU ĐÓ: JwtAuthenticationFilter
  ⚠ chỉ kiểm tra chữ ký + hạn; KHÔNG kiểm tra tài khoản còn hoạt động, KHÔNG có thu hồi  →  smoke test 19: HTTP 200 sau khi khóa
  ⚠ token không có "loại" (scope) → mọi token đều như nhau
  ⚠ token sai/thiếu → request đi tiếp không xác thực → Spring trả 403 (không phải 401)
```

## 3. Thiết kế đích

### 3.1. Mô hình token

Mọi JWT mang: `sub` (username), `iss=taskify`, `iat`, `exp`, `userId`, `scope`, `tv` (tokenVersion). Access token có thêm `role`.

| `scope` | Dùng để | TTL | Chấp nhận ở đâu |
|---|---|---|---|
| `ACCESS` | Gọi mọi API, kết nối WebSocket | `jwt.expiration` (24h — P3-14 sẽ giảm) | `JwtAuthenticationFilter`, WS interceptor |
| `OTP_PENDING` | Chỉ để gọi `/auth/otp/verify` và `/auth/otp/resend` | 10 phút | **Chỉ** hai endpoint đó (đọc từ body, không qua filter) |
| `PWD_CHANGE` | Chỉ để gọi `/auth/password/initial` | 10 phút | **Chỉ** endpoint đó |

Filter chỉ xác thực token `ACCESS`, đồng thời yêu cầu: user tồn tại, `enabled`, `tv == user.tokenVersion`. Token cũ (không có `scope`/`iss`/`tv`) bị từ chối → **mọi người phải đăng nhập lại một lần sau khi triển khai** (mong muốn).

`tokenVersion` tăng khi: khóa tài khoản, đổi role, đổi mật khẩu, kích hoạt, đặt lại mật khẩu, `logout-all`. → mọi token đang lưu hành của user đó chết ngay.

### 3.2. Luồng đăng nhập mới

```
POST /api/auth/login {username, password}
  ├─ throttle: (username|IP) đang khóa? → 429      ├─ IP vượt 10 lần/phút? → 429
  ├─ sai mật khẩu/tài khoản khóa/chưa kích hoạt → 401 "Sai tên đăng nhập hoặc mật khẩu" (chung một thông báo)
  └─ đúng ──┬─ mustChangePassword ──► 200 {nextStep:"CHANGE_PASSWORD", preAuthToken(PWD_CHANGE)}
            ├─ vai trò cần OTP ─────► gửi OTP (LOGIN) ► 200 {nextStep:"OTP", preAuthToken(OTP_PENDING), maskedEmail}
            └─ còn lại ─────────────► 200 {nextStep:"NONE", token(ACCESS), userId, username, fullName, role}

POST /api/auth/password/initial {preAuthToken, newPassword}     (scope PWD_CHANGE, PasswordPolicy)
  └─ đổi mật khẩu, mustChangePassword=false, tokenVersion++ ──► tiếp tục như bước "đúng" ở trên (có thể sang OTP)

POST /api/auth/otp/verify {preAuthToken, code}                  (scope OTP_PENDING; username lấy TỪ TOKEN)
  ├─ đúng → 200 {nextStep:"NONE", token(ACCESS), ...}
  ├─ sai  → 401 "còn N lần thử";  sai lần thứ 5 → OTP bị hủy, phải đăng nhập lại
  └─ hết hạn / không có OTP → 401

POST /api/auth/otp/resend {preAuthToken}                        (cooldown 60s → 429; hủy OTP cũ, tạo OTP mới)

POST /api/auth/activate {identifier, code, newPassword}          (tài khoản chưa kích hoạt; OTP purpose=ACTIVATION, hạn 72h)
```

`LoginResponse` (giữ tương thích với frontend cũ: `token`, `userId`, `username`, `fullName`, `role`, `otpRequired`):
`{ token, preAuthToken, nextStep, otpRequired, mustChangePassword, userId, username, fullName, role, maskedEmail, expiresInSeconds, resendCooldownSeconds }` — khi `nextStep != NONE` thì `token/userId/fullName/role` **rỗng**.

**OTP:** 6 chữ số (`SecureRandom`), hạn 5 phút (kích hoạt 72h, đặt lại mật khẩu 10 phút), tối đa 5 lần thử, so sánh thời gian hằng số, gửi mã mới ⇒ hủy mã cũ cùng mục đích. Email tiếng Việt.

### 3.3. Phân quyền theo đề tài — `TopicAccessService`

| Vai trò | `isOwner(topic)` (quản lý) | `isMember(topic)` (xem/tham gia) |
|---|---|---|
| ADMIN | ✅ luôn | ✅ |
| DEPARTMENT_ADMIN | ✅ nếu workspace của đề tài thuộc **khoa mình** | ✅ (= owner) |
| LECTURER | ✅ nếu là **giảng viên hướng dẫn** của đề tài | ✅ (= owner) |
| STUDENT | ❌ | ✅ nếu có đăng ký **đã duyệt** với đề tài |
| Vai trò khác (tùy biến) | ❌ | ❌ |

- API có hai dạng: `requireOwner(topic)` / `requireMember(topic)` (lấy user hiện tại từ SecurityContext) và `isOwner(topic, user)` / `isMember(topic, user)` (nhận user tường minh — **bắt buộc** cho WebSocket vì luồng WS không có SecurityContext).
- Lỗi trả **403** kèm thông báo tiếng Việt ("Bạn không có quyền với đề tài này").
- Nguyên tắc: `@PreAuthorize` theo vai trò là lớp 1; `TopicAccessService` là lớp 2 (theo **đối tượng**); id do client gửi (`studentId`, `lecturerId`, `userId`) luôn được đối chiếu với người dùng hiện tại.

### 3.6. Lưu trữ file

Bảng `stored_files(id, stored_name UNIQUE, original_name, content_type, size_bytes, owner_id, created_at, ref_type, ref_id)`.

- **Upload:** đuôi ∈ `pdf, doc, docx, xls, xlsx, ppt, pptx, zip, rar, png, jpg, jpeg, txt`; magic bytes phải khớp đuôi (txt: không NUL, UTF-8 hợp lệ); tối đa `20MB` (env); tên lưu `{uuid}.{đuôi}`; tên gốc chỉ để hiển thị (bỏ đường dẫn, ký tự điều khiển, tối đa 200 ký tự); ghi vào `app.upload.dir`.
- **Gắn vào báo cáo:** `progress/create` nhận `fileUrl` dạng `/api/secure/files/{storedName}` → tra `StoredFile`, **owner phải là người đang gọi**, chưa gắn nơi khác → gán `ref`.
- **Tải:** quyền = chủ file **hoặc** ADMIN **hoặc** (file gắn báo cáo) `isOwner(topic của báo cáo)`. SV **không** tải file của SV khác. `Content-Disposition` dùng `ContentDisposition…filename(originalName, UTF_8)` (tên tiếng Việt đúng), `X-Content-Type-Options: nosniff`.
- **Tương thích dữ liệu cũ:** runner `LegacyFileBackfill` (idempotent) tạo `StoredFile` cho các báo cáo đã có `fileUrl` (chủ = SV nộp báo cáo).
- **Dọn rác:** job hằng đêm xóa file chưa gắn quá 24h.

### 3.8. Kích hoạt tài khoản & chính sách mật khẩu
